# 数据库设计说明

> 本文档用于课设报告，也是将来"把系统交到别人手里"时的交接材料。
> 建表语句的**唯一来源**是 `backend/app/db/schema.py`，本文档与它保持一致。

---

## 一、总体设计

### 1.1 为什么是四张表

系统的业务链条是「用户 → 数据集 → 图表 → 大屏」，每张表正好对应一环：

```
Users (账号)
  │
  ├─1:N─> Datasets (上传并清洗后的数据)
  │          │
  │          └─1:N─> Charts (用数据生成的具体图表)
  │
  └─1:N─> Dashboards (把图表组装成的大屏)
```

### 1.2 三条贯穿全表的设计决定

**决定一：每张业务表都有 `UserID`，且代码层强制过滤。**
这是"数据隔离"的物理基础。`Datasets`、`Charts`、`Dashboards` 三张表都带
`UserID` 字段，并且 `backend/app/db/data.py` 里**每一个函数**的第一个参数
都是 `user_id`，每条 SQL 都带 `WHERE UserID = ?`。
这一条由自动化测试守着（见 `backend/tests/test_isolation.py`）。

**决定二：大数据存成 JSON，而不是拆成"宽表"。**
`Datasets.DataJson` 存的是整份数据的 JSON 数组。
- 好处：用户上传的表格**列是不确定的**（可能 5 列，也可能 30 列），
  拆成固定表结构是不可能的；存 JSON 可以容纳任意形状的数据。
- 代价：**存成 JSON 之后就不能用 SQL 查询了**（不能 `WHERE`、不能 `JOIN`）。
  它相当于一个"存档柜"，不是"可检索的仓库"。
  这一点必须如实说明 —— 它是课设范围内合理的设计，但**不是**大数据量下的做法。

**决定三：不保存用户上传的原始文件。**
只保存"解析并清洗后的数据"和"做过哪些清洗"的配方（`CleaningLogJson`）。
理由：省磁盘、少一份隐私风险、避免"原始文件和清洗结果不一致"的困惑。

## 二、表结构

### 2.1 Users（用户）

| 字段 | 类型（SQLite / SQL Server） | 说明 |
| --- | --- | --- |
| UserID | INTEGER PK / INT IDENTITY PK | 主键 |
| Username | TEXT(64) / NVARCHAR(64) | 用户名，**唯一索引** |
| PasswordHash | TEXT(255) / NVARCHAR(255) | **加密后的密码**，绝不存明文 |
| DisplayName | TEXT(64) / NVARCHAR(64) | 显示名 |
| Role | TEXT(16) / NVARCHAR(16) | student / demo |
| IsActive | INTEGER / BIT | 是否启用 |
| CreatedAt | TEXT / DATETIME2 | 创建时间 |
| LastLoginAt | TEXT / DATETIME2 | 最近登录时间 |

**密码存储格式**：

```
scrypt$n=16384,r=8,p=1$<盐的base64>$<哈希的base64>
```

用 `scrypt`（Python 标准库自带）而不是 MD5/SHA256，因为后者算得太快，
显卡每秒能试几十亿次，弱密码几分钟就被撞出来。
`scrypt` 故意算得慢、还吃内存，让暴力破解变得极其昂贵。
算法参数写进字段里，是为了将来提高强度时**老密码依然能验证通过**。

**每个密码都有独立的随机盐**，所以两个人用同样的密码，库里存的值也不同
（这一点是实测验证过的）。

### 2.2 Datasets（数据集）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| DatasetID | 自增主键 | |
| UserID | 整数，外键 → Users | **数据隔离的依据** |
| Name | 文本 | 数据集名称 |
| SourceFileName | 文本 | 来源文件名（仅记录，不保存文件本体） |
| SourceSheet | 文本 | Excel 的工作表名 |
| RowCount / ColumnCount | 整数 | 行数 / 列数（冗余存储，避免为了显示数字去解析整份 JSON） |
| ColumnsJson | 长文本 | 列信息：列名、推断出的类型、缺失值数量 |
| DataJson | 长文本 | **数据本体**（JSON 数组） |
| CleaningLogJson | 长文本 | 清洗步骤记录（做了什么、影响多少行） |
| CreatedAt / UpdatedAt | 时间 | |

### 2.3 Charts（图表）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| ChartID | 自增主键 | |
| UserID | 整数，外键 | 隔离依据 |
| DatasetID | 整数，外键，可空 | 数据来源 |
| Title | 文本 | 图表标题 |
| ChartType | 文本 | bar / line / pie / scatter / race / map … |
| ConfigJson | 长文本 | ECharts 配置 |

### 2.4 Dashboards（大屏）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| DashboardID | 自增主键 | |
| UserID | 整数，外键 | 隔离依据 |
| Title | 文本 | 大屏标题 |
| LayoutJson | 长文本 | 每个面板的位置与尺寸 |
| ShareToken | 文本，**唯一索引**，可空 | 只读分享链接的"钥匙" |
| IsPublic | 布尔 | 是否开启分享 |
| CreatedAt / UpdatedAt | 时间 | |

## 三、数据隔离是怎么做到的

分三层，缺一层都不算做到位。

### 第一层：数据表带 UserID

已在上面说明。这只是前提，光有字段不等于隔离。

### 第二层：代码层强制过滤（**关键**）

`backend/app/db/data.py` 的约定：

```python
def get_dataset(user_id: int, dataset_id: int) -> dict | None:
    return query_one(
        "SELECT * FROM Datasets WHERE DatasetID = ? AND UserID = ?",
        [dataset_id, user_id],
    )
```

规矩有两条，都是为了让"漏掉隔离"这件事变得**显眼**：
1. 每个函数第一个参数必须是 `user_id`（扫一眼签名就知道）；
2. 每条 SQL 必须带 `UserID = ?`。

还有一条安全细节：**查不到、或不属于当前用户，一律返回"空"，
不区分"不存在"和"不是你的"** —— 否则别人可以通过试探来猜出系统里有哪些数据。

### 第三层：自动化测试守着

`backend/tests/test_isolation.py` 做两件事：

- **动态验证**：真实建两个用户、各造数据，然后让甲去偷乙的数据，
  逐个验证"查不到、改不动、删不掉"，并且反向确认甲操作自己的数据是正常的
  （避免"为了安全把功能锁死"）。
- **静态检查**：扫描 `data.py` 里每一个函数，确认都以 `user_id` 为首参数；
  用 AST 解析出所有 SQL 字符串，确认针对业务表的查询都带隔离条件；
  并检查 SQL 里没有写死任何数据库专有的函数。

**当前结果：33/33 通过。**

## 四、唯一的例外：只读分享链接

`get_shared_dashboard(token)` 是**刻意不做用户隔离**的查询 ——
拿到分享链接的人不需要登录也能看大屏。因此它被加了三道锁：

1. 只有 `IsPublic = 1`（用户主动开过分享）的才返回；
2. 只返回大屏本身，**不返回任何用户信息**；
3. token 是 `secrets.token_urlsafe(24)` 生成的随机长串，猜不出来；
   长度不足 16 位直接拒绝。

这三道锁由静态测试守着：一旦有人改坏了 `IsPublic = 1` 这个条件，测试会失败。

## 五、切换到学校 SQL Server 的步骤

代码里已经**同时写好**两套建表语句，切换**只需要改配置**。

### 驱动选型：为什么用 pymssql 而不是微软官方驱动

| 方案 | 体积 | 需要管理员权限 | 说明 |
| --- | --- | --- | --- |
| **pymssql（本项目采用）** | 3.1 MB | **不需要** | 安装包自带 FreeTDS 等底层库，一条 pip 命令搞定 |
| pyodbc + msodbcsql18 | 约 60 MB | 需要（sudo） | 官方路线，但要装系统级 ODBC 驱动 |

选 pymssql 的理由很实际：**它对使用者少一道门槛**。装它不需要管理员密码，
也不会往系统里塞东西。代码同时兼容两者（`app/db/drivers.py` 负责探测），
装了 pymssql 就优先用它。

> 一个容易踩的坑：两个驱动的**参数占位符不一样** —— pymssql 用 `%s`，
> pyodbc 用 `?`。写死任何一种，换驱动时每条带参数的 SQL 都会报错，
> 而且报错信息非常难懂。本项目把这个差异收在 `dialect.py` 里自动处理，
> 并做了正确的转义顺序（先转义字面量 `%`，再替换 `?`）。

### 第 1 步：填配置（使用者自己操作）

打开 `backend/.env`：

```ini
DB_MODE=mssql
MSSQL_HOST=<学校给的服务器地址或IP>
MSSQL_PORT=1433
MSSQL_DATABASE=<学校给的库名>
MSSQL_USER=<学校给的登录用户名>
MSSQL_PASSWORD=<你自己的密码>
```

**密码由使用者自己填写。** 项目代码里没有任何明文密码，
所有密钥都从 `.env` 读取，而 `.env` 在 `.gitignore` 里，不会被提交或分享。

### 第 2 步：装驱动（已完成）

```bash
cd backend && .venv/bin/pip install pymssql
```

不需要 sudo，不需要装系统级 ODBC 驱动。

### 第 3 步：先跑体检，别急着切

```bash
cd backend && PYTHONPATH=. .venv/bin/python tests/check_mssql.py
```

这个工具会依次检查七件事，**每一步失败都给出人话的原因**：

1. 配置填全了没有（只报"已填写/为空"，**不打印密码**）
2. 驱动装了没有
3. 网络能不能通到 1433 端口
4. 账号密码能不能通过校验
5. 指定的库名存不存在
6. **有没有建表权限**（用一张临时表试，试完立刻删）
7. **中文存进去再读出来会不会乱码**

> 第 6、7 两条是中文项目最容易翻车的地方：
> 权限不足会导致部署时才发现建不了表；编码没配对会让"广东"变成问号，
> 而且往往在演示用到中文时才暴露。

### 第 4 步：确认无误后再改 `DB_MODE` 并重启

启动时会自动检查表在不在，不在就建。**不需要手动执行任何 SQL。**

### 切换前必须知道的三件事

1. **需要 `CREATE TABLE` 权限**。本项目用的账号在自己的库里有权限；
   若学校账号只有读写权限，需要让老师开权限，
   或由老师预先按本文档第二节的表结构建好表。
2. **`NVARCHAR(MAX)` 字段单字段上限 2GB**。按本项目上传限制
   （≤5MB、≤5000 行），远达不到上限。
3. **库名必须填使用者自己的那个库**（学号+姓名）。填了没有权限的库时，
   SQL Server 返回的是 `Login failed for user` 而**不是**「库不存在」——
   一个权限问题伪装成密码问题。诊断办法见下面的排错清单。

### 换库时才暴露的 5 个问题（重要）

这套代码在本地 SQLite 上 33 项测试全绿，但连上真实 SQL Server 后接连暴露 5 个 bug，
全部是「SQLite 宽容、SQL Server 严格」造成的。详见 `README.md` 第七章：

1. 无别名表达式列返回**空列名**，`as_dict=True` 直接抛异常
2. `RowCount` 撞 SQL Server **保留字** `ROWCOUNT`
3. 唯一索引**把 NULL 当成值**，导致「全表只能有一个大屏」
4. `LIMIT` 不是 SQL Server 语法（要用 `TOP`）
5. `execute()` 对 UPDATE 也去取自增 ID，把 `rowcount` 覆盖成 `-1`

这些问题已在代码里修掉，并各自配了自动化防线
（`tests/_sqlscan.py`、`tests/test_schema_portability.py`、扫描器自检）。

## 六、可以写进课设报告的"设计亮点"

1. **密码从不明文存储**，用标准库 `scrypt` 加随机盐，且格式自带算法参数以便升级。
2. **数据隔离有三层保障**（字段 + 代码约定 + 自动化测试），
   并且测试同时做动态验证和静态扫描 —— 能防止将来新加函数时漏掉隔离。
3. **同一套代码同时支持两种数据库**，差异全部收在 `dialect.py` 一个文件里。
   开发时用本地 SQLite（零配置、断网可用），交付时切学校 SQL Server 只改配置。
   连驱动之间的参数占位符差异（`?` 与 `%s`）都做了自动适配和正确转义。
4. **登录失败次数限制**：连续输错 5 次锁定 60 秒，抵御暴力猜密码。
5. **登录失败提示不泄露用户名是否存在**（两种情况返回完全相同的话术）。
6. **令牌带签名和有效期**，篡改内容或签名立即失效（已实测）。
